search_agent — how it works

A daily AI-news digest. Feeds in, one LangGraph run, a bulletin you read in the browser. It runs on one laptop with Docker and SQLite. Each press records its token cost.

the clock — every 3 hours

APScheduler, inside the API process. It runs collect and stops there: no model, no cost.

DEMO_MODE winds no clock at all — a recording polls nothing.

a person — the press on /runs

The only paid action in the whole app. One click gets a question, not a run; only the answer is a POST. You pick the models there; every new bulletin has English and Turkish views.

collect

poll every feed, keep what is new. A 404 is that source's failure, not the run's.

→

dedupe

one story filed by five outlets is one story. Fuzzy title match; the loser is marked, never deleted.

→

enrich

give thin items a body, cheapest tier first: the feed's own HTML, then a fetch, then one Tavily credit.

→

summarize

one branch per article, 10 in flight. Each branch commits its own summary row before it returns.

→

rank ×3

the only step that sees the whole day, read three times shuffled and aggregated by Borda count. How far the three agreed ships on the bulletin.

→

translate

complete Turkish story prose, editor note and reasons; reuse valid cached translations. A failure preserves the previous bulletin.

→

persist

publishes the day as a new version, not a second entry; runs the free checks over what it published; closes the run.

every node writes its own run_steps row as it runs  ·  nothing new today? it ranks the existing English pool and reuses completed translations

SQLite · data/app.db · WAL, FTS5

sources · articles · summaries · summary_translations · bulletins · bulletin_items · runs · run_steps · verdicts · eval_results

The graph state carries ids, not bodies — bodies stay here, which is what keeps a hundred parallel branches cheap.

There is no checkpoint file. A summary belongs to its article and is committed by the branch that paid for it, so a run that dies loses the ranking and nothing else; the next press ranks what is already here.

A press — one selection, two complete stored views

collect     poll enabled sources
dedupe      canonical URLs and duplicate titles
enrich      feed body, article fetch, capped search
summarize   Send ×N, English rows committed independently
rank        standing English pool, 3 shuffled readings
translate   selected prose + note + reasons; reuse valid cache
persist     one bilingual bulletin version, one ordered item list

Then you open /, read it, and mark one summary wrong and say why; that verdict goes to the verdicts table. /runs/<id> shows the paid and free steps with their tokens, their cost, how long each one took, and what the checks made of the result. Nothing above happens on its own: the clock only polls feeds, and the bulletin waits for a press.

quality/ and evals/ — the free half and the paid half

src/ainews/quality/ is product code. The deterministic checks call no model and write no row, so persist runs them and /runs/<id> draws them.

src/ainews/evals/ is the half that spends. It is imported by neither the pipeline nor the web layer — only by cli.py, so the app still has exactly one button that spends money.

  • pytest, offline, over a recorded fixture
  • categorized wrong feedback with optional notes
  • a sampled grounding judge; wrong-only examples do not calibrate it
  • production agreement: min(τ, chance-corrected Jaccard)
  • two prompts over the same frozen bodies
